## 🎯 概要

**AP Audio Probe** は、ap-comp が生成した楽曲が**レシピの指示どおりに鳴っているか**を測る検証ツールです。音源と `recipe.json` を突き合わせ、セクションごとに実際の音を測って報告します。

主な用途は、**インスト指定のセクションにボーカルが混入していないか**の検出です。ap-comp のセクションプロンプトには `Instruments only — no lead vocal, no vocalised syllables` と明示されていますが、これを検証する仕組みは従来ありませんでした。間奏にハミングが乗っても、そのまま高スコアが付きます。

生成の良し悪し（メロディ、歌のうまさ、曲としての出来）は対象外です。ここで分かるのは「指示に反していないか」だけで、音楽的な判断は実聴に残ります。

## 💎 特徴と設計思想

### 🎧 伴奏を除去してから測る（separate.py）

EDM の saw 系パッドやコードは、**歌声と同じ帯域に倍音ごと乗ります**。帯域エネルギーだけでシンセと歌を見分けようとすると誤検出が避けられません。

そこで Demucs でボーカル stem を分離し、伴奏を実際に取り除いてから測ります。判定が原理的に素直になり、実測でも歌唱区間と間奏で **25dB** の差が付きます。Apple Silicon の MPS で3分の曲に20秒程度。分離済みなら再実行しません。

### 📏 閾値は曲ごとの相対（vocals.py）

固定の絶対値では曲を跨いで機能しません。Demucs は伴奏を完全には除去しきれず微量が漏れ、そのレベルは曲ごとに違うためです。

そこで**その曲の歌唱セクションの RMS 中央値**を基準に取り、そこから 12dB 以内、または有声率 20% 超を「声あり」と判定します。物差しを曲自身から作ることで、ジャンルや音圧が変わっても同じ基準で読めます。

### 🎣 境界の食い込みは中身から外す（vocals.py）

歌い出しは境界の手前から始まることがあり（弱起）、歌尾は境界を越えて伸びます。区間平均はこの1秒弱に引きずられ、実測では声が立つのが最後の 0.9 秒だけの間奏で、RMS が **−50.9dB から −30.0dB へ跳ねて違反として上がりました。**

そこで、**隣が歌唱セクションである側の端**に接した声は 2.0 秒までを食い込みと見なし、測定から外して秒数を併記します。中ほどに現れる声はそのまま残るため、混入の検出力は変わりません（下の陽性対照で確認済み）。

### 🧾 区間の基準はレシピ（recipe.py）

セクションの境界は `recipe.json` の `start_seconds` / `end_seconds` が唯一の基準です。インスト指定かどうかは、セクションプロンプトに `Instruments only` が含まれるかで判定します（ap-comp のプロンプト規約に依存）。

音源がレシピの宣言尺より短いことは普通に起きるため（Lyria が Outro を畳む）、各区間は実尺で clamp し、不足があれば `尺不足` として報告します。

### 🚦 判定は出すが、止めない

違反を見つけても失敗扱いにはせず、数字と根拠を並べて返します。生成品質の問題はプロンプト調整と手動での作り直しで対処する運用のため、自動ゲートは設けていません。

## 🚀 クイックスタート

必要なもの: Python 3.14 / Google Cloud SDK（`gsutil`）/ ffmpeg（ラウドネス測定が呼びます）。

`--device` の既定は `mps` でフォールバックがありません。Apple Silicon 以外では `--device cpu` の明示が要ります。

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

初回実行時に Demucs の学習済みモデル（約 300MB）が自動で取得されます。

### 実行（コピペ用）

`<job_id>` は Slack 通知、または ap-mcp の `get_music_detail` から取れます。

```bash
JOB=comp-20260811-014550-54471f266c38

gsutil cp gs://ap-music/music/$JOB/master.wav  audio/$JOB.wav
gsutil cp gs://ap-music/music/$JOB/recipe.json recipes/$JOB.json

.venv/bin/python -m probe audio/$JOB.wav recipes/$JOB.json
```

```
python -m probe <audio> <recipe> [--out OUT] [--device DEVICE]
```

| 引数 | 必須 | 既定値 | 説明 |
|---|:---:|---|---|
| `audio` | ✅ | — | 音源（mp3 / wav） |

| `--device` | | `mps` | Demucs の実行デバイス（`mps` / `cpu` / `cuda`） |

## 📊 出力の読み方

```
Split the Role  /  126 BPM
実尺 174.3s  (レシピ指定 180s)

section    指定     区間                vocal RMS     peak     有声率  判定
----------------------------------------------------------------------------
Intro      インスト   0-8.0s               -45.9dB   -28.5dB     1%  クリーン
Verse      歌唱     8-38.0s              -21.6dB    -7.6dB    90%  -
Chorus     歌唱     38-74.0s             -19.3dB    -3.5dB    95%  -
Interlude  インスト   74-86.0s             -45.5dB   -39.9dB     0%  クリーン
Verse 2    歌唱     86-116.0s            -20.9dB    -7.2dB    87%  -
Chorus 2   歌唱     116-160.0s           -19.6dB    -3.6dB    96%  -
Outro      インスト   160-174.3s           -44.5dB   -25.5dB     4%  クリーン (食い込み 0.1s 除外、尺不足 5.7s)
----------------------------------------------------------------------------
歌唱セクションの基準値: -20.3 dBFS (この値から 12dB 以内、または有声率 20% 超で「声あり」)
※ 「食い込み」は隣の歌唱セクションから端に届いた声(弱起や歌尾)です。

✓ インスト指定セクションはすべてクリーン
```

`vocal RMS` はボーカル stem の音量です。歌唱セクションとインストセクションの差が大きいほど、指示が守られていることになります。上の例では 25dB 差、間奏の有声率は 0%。

## 🧪 検出力と、その限界

クリーンな曲を測って「違反なし」と出ても、それは検出できることの証明にはなりません。何を渡しても「クリーン」を返す実装でも同じ結果になるためです。

そこで `scripts/calibrate.py` が**陽性対照**を合成します。間奏に歌声を意図的に混ぜた音源を作り、混入量を変えながら検出できるかを測ります。

```bash
.venv/bin/python scripts/calibrate.py audio/<name>.wav recipes/<name>.json
```

実測結果（歌唱に対する相対量で混入）:

| 混入量 | 間奏の vocal RMS | 有声率 | 判定 |
|---:|---:|---:|---|
| ±0dB | −19.9dB | 93% | ★検出 |
| −6dB | −26.1dB | 90% | ★検出 |
| −12dB | −33.0dB | 83% | ★検出 |
| −18dB | −40.8dB | 25% | ★検出 |
| −24dB | −45.3dB | 0% | 見逃し |
| −30dB | −45.4dB | 0% | 見逃し |

**歌唱より 18dB 小さい混入までは検出できます。** −24dB 以下は Demucs の分離漏れ（この曲では −45dB 前後）に埋もれ、クリーンな間奏と区別がつきません。**これは閾値調整では超えられない手法の限界**で、感度を上げたければ分離の質を上げるしかありません。

実用上は十分です。間奏に −24dB で漏れた残響は「ボーカルが乗っている」とは呼べず、拾えば狼少年になります。

なお感度の下端を支えているのは**有声率のルール**です。RMS の 12dB ルール単独では −12dB 付近までしか届かず、−18dB を拾えているのは有声率 20% 超の条件です。両方を残す理由がここにあります。

## 🎤 歌詞の行落ち検査

Lyria は奇数行のセクションで1行落とすことがあり、ap-comp 側でそれを見ているのは「内部の無音が長いか」という間接的な指標だけです。分離したボーカル stem を faster-whisper で書き起こし、レシピの歌詞と行単位で突き合わせます。

```bash
.venv/bin/python scripts/check_lyrics.py audio/<name>.wav recipes/<name>.json
```

比較は**読み（カタカナ）に正規化**してから行います。漢字と仮名の表記差で不一致になるのを防ぐためです。

### ASR の落とし穴

**stem 全体を一度に書き起こしていません。** whisper は 30 秒窓で処理するため、冒頭のインストが窓に丸ごと入ると無音とみなして幻聴を返します。実測では 0-30s が「ご視聴ありがとうございました」1セグメントに潰れ、**実際には歌われている Verse の6行が「落ちた」と報告されました。** セクションの区間ごとに切って渡すと同じ音源で全行出ます。

**区間ごとに切っても、幻聴は残ります。** 最後の半端な窓が内部で無音に埋められるためです。歌が 161s で終わる Chorus 2（122-162s）の書き起こしが「ご視聴ありがとうございました」で終わり、**歌われている最終行が 43% で「落ちた」と報告されました。** 止まったのは `hallucination_silence_threshold` だけで、末尾の無音を詰める・`vad_filter` を有効にする・`no_speech_threshold` を下げるはいずれも効きませんでした。

**声が一度も鳴らない区間は、書き起こしに回さず空を返します。** 渡せばそこも幻聴で埋まり、**行が丸ごと落ちたセクションを見逃します。**

**歌詞を `initial_prompt` に渡していません。** 認識率は上がりますが、モデルが与えた歌詞に引きずられ、**落ちた行まで書き起こされます。** 検証したい対象を答えとして渡すことになるので、意図的に無指定で回しています。

**英語は比較から外しています。** 日本語 ASR は混ざった英語を安定して聞き取れず、実測では `Split the role` が一貫して `Speed the road` になりました。行は歌われているのに不一致として上がるため、日本語部分だけで判定し、英語のみの行は「判定対象外」と明示します。

### 閾値の根拠

一致率は**一致ブロックの合計**で測ります。最長の連続一致だと、両端の小さな誤認識で分断されて実際より低く出るためです（`境界をここに引け` が `妖怪よ ここに行け` と聞かれた例で 27% まで落ちました）。

実測で校正しています。

| | 一致率 |
|---|---|
| 実際に歌われた行 | 73〜100% |
| 歌われていない行（陰性対照） | 14〜29% |

**両群は 44 ポイント離れており、閾値 45% はその間に収まります。** この分離はテストで固定してあります。

## 🔊 曲間のラウドネス

ap-comp は1曲ずつしか採点しないため、シリーズとして並べたときの音量差は構造的に見えません。配信で効くのはそこです。

```bash
.venv/bin/python -m probe.loudness audio/*.wav
```

BS.1770 の Integrated LUFS・True Peak・LRA を並べ、**曲間の差が 1.0 LU を超えたら**警告します。あわせて **True Peak が −1.0 dBTP を超える曲**を指摘します。サンプルピークを −1.0 dBFS で抑えても、サンプル間のピークはそれを超えるため、ロッシー変換で歪む恐れがあります。

ここで測った 11曲は 1.7 LU 差（−13.2〜−11.5）でした。masterer に音量合わせが無かったためで、ap-comp は 2026-08-15 に目標 −12.5 LUFS へ寄せる処理を入れています（`c2d6894`）。**その日より後に生成された曲を測り直すまで、揃ったかどうかは確定ではありません。**

## 🎛 セクション別の帯域バランス

ap-comp の masterer は 4-10kHz だけを圧縮しています。その定数（`acrossover=split=4000 10000`、`acompressor=threshold`）が実際の曲でどう働いているかを測ります。

```bash
.venv/bin/python -m probe.spectrum audio/<name>.wav recipes/<name>.json
```

判断に使うのは **50ms 窓の短時間レベル**です。セクション全体の RMS は 36 秒を平均してしまい、コンプレッサの検出器が見ている量とは別物になるためです（全区間が「閾値以下」に見えます）。

測れるのは**処理後の音だけ**です。「効いている」ことは言えても、「必要である」ことの証明にはなりません。

11曲で測ると、**サビの短時間レベルは −29.3〜−31.4dBFS で全曲が閾値を超え、閾値超過時間は 11〜43%**。Verse は 2〜13% でほぼ素通りで、「サビだけ抑える」という設計意図は成立していました。ただし超過時間が4倍ばらついており、曲によっては Verse も一緒に踏まれていたため、**ap-comp は 2026-08-15 に閾値を固定の −32.0dBFS から曲ごとの相対（その曲の 4-10kHz 平均 +2.5dB）に変えています**（`c2d6894`）。

> ⚠ `probe.spectrum` は固定の −32.0dBFS のままです。**08-15 より後に生成された曲では、「圧縮域」の列は実際にかかった量ではありません。**

## 🎚 mp3 と master.wav のどちらを測るか

ap-comp は同じ GCS ディレクトリに `audio.mp3`（192kbps）と `master.wav` の両方を置きます。実測した差は次のとおりです。

| | peak | 16kHz 以上 |
|---|---|---|
| `master.wav` | −1.00 dBFS | 19.6 dB |
| `audio.mp3` | **−0.88 dBFS** | 19.5 dB |

- **ボーカル検出なら mp3 で十分。** 判定に使う差が 25dB あるのに対し、符号化による差は 0.1dB 台で結論が動きません。
- **マスタリング・配信の QC は `master.wav`。** mp3 は符号化で波形がオーバーシュートし、ピークが元より高く出ます。配信に出すのは wav なので、出荷物を測るという意味でもこちらです。
